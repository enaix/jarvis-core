# ZS/FS эксперимент: метод, результаты, выводы

Материал для соответствующих разделов ВКР. Числа выверены по `outputs/metrics.jsonl` и `outputs/analysis.json` после финального прогона (1800 metric rows, 4 архитектуры × 2 shots × 3 температуры × 25 вопросов × 3 runs).

---

## 1. Метод

### 1.1. Цель эксперимента

Проверить, способна ли frontier-LLM (gpt-4o) производить структуру в формате `widget` напрямую через prompting — без fine-tuning, который изначально планировался как основной путь. Если такая способность есть, это меняет позиционирование widget-формата: он становится не только мишенью для fine-tuning'а, но и универсальным целевым форматом, достижимым через стандартные prompting-техники.

### 1.2. Задача и набор данных

Задача: на естественно-языковой вопрос модель должна вернуть структурированный ответ в формате `widget` — JSON-дерева из 4 типов узлов (`text`, `block`, `link`, `image`) и 10 hint-меток, размечающих структурно-семантическую роль узла.

Eval-set: 25 синтетических вопросов, охватывающих 7 доменов (recommendation, explanatory, how-to, comparison, list, process, concept). Вопросы подобраны так, чтобы естественные ответы на них имели разную структурную природу (списки, процедуры, сравнения, объяснения).

### 1.3. Архитектуры (типы пайплайнов)

Проверены 4 архитектуры — две прямые и две через промежуточный формат:

- **T1** — direct widget: `вопрос → widget`. Модель сразу выдаёт целевой формат.
- **T2** — text-mediated widget: `вопрос → текст → widget`. Сначала свободный текст-ответ, затем второй вызов модели конвертирует текст в widget.
- **T3** — AXtree-mediated widget: `вопрос → Chrome AXTree → widget`. Модель сначала выдаёт Chrome DevTools Protocol AXTree dump (flat list с parentId/childIds), затем детерминированный адаптер `chrome_axtree_to_widget` переводит его в widget.
- **T4** — text-then-AXtree-mediated widget: `вопрос → текст → AXtree → widget`. Аналог T2, но в качестве промежуточного формального представления используется AXtree вместо widget.

Архитектуры T3 и T4 проверяют гипотезу, что для модели может быть проще генерировать в стандартном веб-формате (AXTree — формат Chrome DevTools, который должен встречаться в обучающих корпусах в большом объёме), а затем механически конвертировать его в widget.

### 1.4. Условия (factorial design)

Каждая архитектура прогоняется в 6 условиях: 2 (shots) × 3 (temperature):

- **Shots**: `zs` (zero-shot, только schema в system prompt) и `fs` (few-shot, K=3 примера в user-messages истории).
- **Temperature**: T=0 (детерминированно), T=0.4 (умеренный sampling), T=0.8 (свободный sampling). В коде хранятся как `seed_mode = fixed/semi/random` для совместимости с историей кода; в отчётности приводятся как T=0/0.4/0.8.

Для каждой ячейки (question × type × shots × T) выполняется 3 повторных run'а с разными `seed`-значениями для устойчивой оценки дисперсии.

**Всего**: 4 × 2 × 3 × 25 × 3 = 1800 модельных вызовов.

### 1.5. Метрики

**Валидность (strict)** — per-row проверка: соответствует ли непосредственный выход модели запрошенному формату?

- Для T1, T2: широт-уровневая schema validity (JSON Schema Draft 2020-12 для widget).
- Для T3, T4: AXtree-уровневая integrity check (корректность ссылок parentId/childIds, единственный root, отсутствие циклов, известность ролей, отсутствие orphan-нод, отсутствие нод с двумя родителями).

Три тира: `valid` (проходит как есть), `soft` (восстанавливается нормализацией), `hard` (необратимая ошибка или unparseable JSON).

Важная методологическая деталь: для T3 и T4 валидность считается **до** применения адаптера `chrome_axtree_to_widget`. Адаптер пермиссивен (восстанавливает part-of-broken AXtrees в валидные widgets через fallback на `block` для неизвестных ролей, visited-set cycle guard, отбрасывание сломанных ссылок), и его recovery маскировал бы реальные ошибки модели. Валидность — заявление о модели, а не о tooling вокруг неё.

**Структурная дисперсия** — для каждой ячейки (q × type × shots × T) вычисляется нормированное Tree Edit Distance (TED, реализация `zss`) между парами из 3 runs, усредняется. Метки нод для сравнения: `type + sorted(hints)`. Нормализация: на сумму размеров деревьев.

**Семантическая дисперсия** — для каждой ячейки извлекается DFS-конкатенация `name`-полей всех нод widget'a (после конверсии в widget), эмбеддируется моделью `all-MiniLM-L6-v2` (sentence-transformers), считается попарная (1 − cos similarity), усредняется.

**Cross-condition divergence** — для каждой пары архитектур (всего 6 пар при 4 типах) считается mean structural distance между выходами для одного и того же вопроса, усреднённое по всем 25 вопросам. Сравнивается с within-type noise (внутренней дисперсией каждой архитектуры).

### 1.6. Модель и инфраструктура

- API: `gpt-4o` через OpenAI Chat Completions
- Эмбеддинги: `sentence-transformers/all-MiniLM-L6-v2`
- TED: `zss` 1.2.0
- Schema validation: `jsonschema` Draft 2020-12
- Stack: Python 3.11

### 1.7. Курация финального таксономии

В ходе работы были также протестированы ablation-варианты `t3_full` и `t3_lean` (упрощённые nested-AXtree представления вместо реального flat-формата Chrome). Они были исключены из финального анализа: реальный flat Chrome AXTree формат (тип `t3_real`, в отчётности — `t3`) методологически честнее, поскольку именно он встречается в обучающих корпусах. Финальная таксономия: T1, T2, T3, T4.

## 2. Результаты

### 2.1. Валидность по условиям

Строгая валидность (% от 225 outputs на условие):

| Условие  | % valid |
|----------|--------:|
| t1/zs    | 54.2%   |
| t1/fs    | 97.8%   |
| t2/zs    | 58.2%   |
| t2/fs    | 100.0%  |
| t3/zs    | 77.3%   |
| t3/fs    | 35.1%   |
| t4/zs    | 45.8%   |
| t4/fs    | 34.2%   |

Ключевые наблюдения:

1. **Прямые архитектуры (T1, T2) с few-shot достигают 97.8% и 100% валидности**. Это значит, что widget-формат как целевой output полностью достижим современной LLM через prompting — fine-tuning не является необходимым условием.

2. **AXtree-опосредованные архитектуры (T3, T4) с few-shot валидность теряют, а не приобретают** (t3: 77% → 35%, t4: 46% → 34%). Гипотеза о пользе промежуточного веб-стандартного формата не подтвердилась.

3. **T4 хуже T3 по обоим shots**. Это контринтуитивно: добавление промежуточного текстового шага к AXtree-генерации (t4 = text → AXtree → widget vs t3 = вопрос → AXtree → widget) ухудшает результат. Объяснение — в характеристиках выхода: t4 outputs в 2-3 раза длиннее (avg ~7000-9700 chars vs ~3000-4500 у t3), что увеличивает количество ID-ссылок, которые модель должна корректно отслеживать. Большинство ошибок T4 — broken childIds, multi-parent claims, неизвестные роли — масштабируются с размером.

### 2.2. Эффект few-shot на дисперсию

Few-shot снижает структурную дисперсию на 28-39% во всех архитектурах:

| Архитектура | struct var zs | struct var fs | reduction |
|-------------|--------------:|--------------:|----------:|
| t1          | 0.459         | 0.281         | -39%      |
| t2          | 0.278         | 0.189         | -32%      |
| t3          | 0.420         | 0.302         | -28%      |
| t4          | 0.460         | 0.300         | -35%      |

Эффект на семантическую дисперсию ещё интереснее — он усиливается с ростом температуры:

| Условие     | T=0   | T=0.4 | T=0.8 |
|-------------|------:|------:|------:|
| t4 zs       | 0.086 | 0.147 | 0.199 |
| t4 fs       | 0.051 | 0.056 | 0.072 |
| **редукция**| -41%  | -62%  | -64%  |

Few-shot anchor влияет сильнее именно там, где sampling даёт модели больше свободы. Это содержательно: при T=0 модель и без шаблона относительно стабильна (для многих ячеек дисперсия буквально 0.000 — выход детерминирован), при высокой температуре she-shot задаёт ожидаемый объём и стиль ответа.

### 2.3. Качественный анализ дисперсии: case-study на q22

Top-1 high-variance cell в эксперименте — `q22 / t4 / zs / T=0.8` (mean pair-dist 0.523, в 2× больше следующей по списку ячейки). Вопрос: "How do I apply for a passport?". Три runs дали радикально разный уровень детализации:

- **Run A** (~20 слов): только названия секций ("General Procedure", "Receiving Your Passport", "Passport Renewals"). Модель решила выдать outline.
- **Run B** (~370 слов): один заголовок + 6 длинных параграфов с пошаговыми инструкциями (документы, форма DS-11, acceptance facility, обработка, доставка). Модель решила расписать всё.
- **Run C** (~50 слов): названия секций + 1-2 фразы детализации в каждой. Гибрид между outline и full guide.

Это иллюстрирует, что без few-shot anchor модель **самостоятельно решает уровень детализации** ответа, и для open-ended процедурных вопросов это решение нестабильно от прогона к прогону. Семантические эмбеддинги skeleton-варианта и full-guide-варианта расходятся не на стилистическое различие, а на различие в количестве и характере семантики. Эта вилка объяснимо устраняется при добавлении примеров, фиксирующих ожидаемый формат и объём.

### 2.4. Cross-architectural divergence

Расхождение между парами архитектур (mean structural distance, averaged across 25 questions):

| Пара      | struct divergence | seman divergence | exceeds within-type noise? |
|-----------|------------------:|-----------------:|:---------------------------|
| t1 ↔ t2   | 0.656             | 0.137            | YES (max noise 0.370)      |
| t1 ↔ t3   | 0.842             | 0.140            | YES                        |
| t1 ↔ t4   | 0.847             | 0.164            | YES                        |
| t2 ↔ t3   | 0.886             | 0.187            | YES                        |
| t2 ↔ t4   | 0.789             | 0.111            | YES                        |
| t3 ↔ t4   | 0.617             | 0.192            | YES                        |

Все 6 пар: cross-type расхождение превышает внутри-типовой шум. Это значит, что архитектурный выбор реально определяет форму выхода — это не случайная вариация, разные пайплайны производят систематически разные деревья.

Within-type variance (от 0.234 у t2 до 0.380 у t4) меньше cross-type divergence (0.617-0.886) в 2-3 раза — соотношение сигнал/шум адекватное для содержательных выводов.

### 2.5. Эффект температуры

Структурная дисперсия монотонно растёт с температурой, как и ожидалось:

| Температура | Средняя дисперсия |
|-------------|------------------:|
| T=0         | 0.205             |
| T=0.4       | 0.358             |
| T=0.8       | 0.446             |

Это служит **sanity check** методологии: метрика реагирует на sampling-параметр в ожидаемом направлении, что подтверждает её осмысленность.

### 2.6. Ручная валидация на subset'е

Дополнительно к автоматическим метрикам проведена ручная оценка качества на subset'е выходов: 5 случайных карточек на условие (всего 40 карточек), оценённых одним рейтером по 5-балльной Likert-шкале с явными якорями:

- **1** — broken / unusable (структурный fail, не отвечает на вопрос)
- **2** — correct content but poorly structured
- **3** — ok with some flaws
- **4** — good, minor issues
- **5** — excellent

Карточки перемешаны и условия скрыты до завершения оценки (blind rating).

Mean rating по условиям (N=5 на условие, ±std):

| Условие | Manual mean ± std | Widget % valid | Strict % valid |
|---------|------------------:|---------------:|---------------:|
| t1/zs   | 4.8 ± 0.45        | 54.2%          | 54.2%          |
| t1/fs   | 3.4 ± 0.89        | 97.8%          | 97.8%          |
| t2/zs   | 4.8 ± 0.45        | 58.2%          | 58.2%          |
| t2/fs   | 4.8 ± 0.45        | 100.0%         | 100.0%         |
| t3/zs   | 1.8 ± 1.10        | 100.0%         | 77.3%          |
| t3/fs   | 2.4 ± 0.55        | 99.3%          | 35.1%          |
| t4/zs   | 2.6 ± 1.52        | 100.0%         | 45.8%          |
| t4/fs   | 3.0 ± 0.71        | 100.0%         | 34.2%          |

Для t1, t2 widget и strict совпадают (нет адаптера). Для t3, t4 видна разница: widget-метрика даёт ложные 100% для большинства условий, strict-метрика показывает реальную картину.

Ключевые наблюдения:

**1. Manual rating подтверждает порядок архитектур по качеству:** T1 ≈ T2 >> T4 > T3. Это совпадает с автоматической оценкой при использовании strict-метрики (pre-adapter), но не совпадает с widget-уровневой метрикой (post-adapter), которая ставит T3/T4 в 100%. Это эмпирически подтверждает методологическое решение измерять валидность до адаптера: пермиссивная recovery маскирует ошибки, которые человеческий рейтер легко замечает.

**2. Soft-error виджеты не страдают в восприятии:** виджеты с status='soft' (восстанавливаемые нормализацией) получили средний rating 5.00, выше чем status='valid' (mean 2.98). Это парадоксально только при поверхностном взгляде: soft-нормализация (заполнение пустых children, корректировка hints) приводит widget в читабельное состояние без потери смысла, а большинство widget-valid рейтингов 1-2 — это широт-уровневые-валидные но AXtree-структурно-сломанные t3/t4 outputs, восстановленные адаптером. Это снова подтверждает strict-pre-adapter измерение как методологически корректное.

**3. Trade-off, не уловимый автоматикой — few-shot anchors verbosity:** T1/fs получил manual mean 3.4, в то время как T1/zs — 4.8 (несмотря на 98% vs 54% строгой валидности). Качественный анализ карточек выявил систематическую причину: few-shot примеры в эксперименте короткие (3-5 узлов), и модель в T1/fs воспроизводит эту краткость напрямую, выдавая валидные но информационно-скудные виджеты. T2/fs не страдает от этого эффекта, потому что промежуточный текстовый шаг (свободный ответ модели в обычной verbosity) сохраняет объём содержания до этапа структурирования.

Это методологически важное наблюдение: автоматические метрики (валидность, TED, embedding distance) измеряют **корректность формата и стабильность структуры**, но не **информационную полноту**. Manual rating ловит этот аспект качества, который иначе остался бы невидимым.

**4. Корреляция automatic ↔ manual (Spearman ρ по 8 условиям):**

- widget-level vs manual: ρ = **−0.533** (p = 0.174) — отрицательная: автоматика и человек системно расходятся
- strict-level vs manual: ρ = **+0.342** (p = 0.408) — положительная

Сдвиг почти на 0.9 пункта при переходе от widget- к strict-метрике эмпирически подтверждает методологический выбор: strict (pre-adapter) валидность согласуется с человеческим суждением, widget (post-adapter) — нет. p-value не достигают значимости при N=8 условиях, но **направление сдвига** — содержательная находка независимо от силы корреляции.

**5. Per-architecture корреляция rating ↔ node_count выявляет особенность T2:**

| Архитектура | Pearson r |
|-------------|----------:|
| T1          | +0.91     |
| T2          | **−0.28** |
| T3          | +0.90     |
| T4          | +0.71     |

T2 — единственная архитектура, где количество узлов **не предсказывает** субъективное качество. У T1, T3, T4 рейтинг сильно зависит от размера выхода (больше узлов = выше оценка). У T2 связь отсутствует, что отражает её архитектурную особенность: промежуточный текстовый шаг фиксирует verbosity отдельно от структурирования, и T2 даёт стабильно хорошие виджеты независимо от их размера. Это согласуется с другими находками о T2 (минимальная within-type variance 0.234, наивысшая семантическая стабильность через примеры).

**6. T1/fs anomaly — методологический limit автоматических метрик:** strict-валидность T1/fs (98%) высокая, но manual rating (3.4) ниже чем у T1/zs (4.8). Эта аномалия в одиночку снижает strict-vs-manual Spearman. Это означает что даже strict-метрика **не ловит verbosity matching** — этот аспект качества обнаруживается только через manual rating. См. пункт 3 выше про few-shot anchoring verbosity.

### 2.7. Content density: useful text vs JSON overhead

Дополнительный анализ выходов выявил различие между **raw output size** (полная длина строки от модели, включая всю JSON-разметку) и **useful text content** (сумма длин всех `name`-полей при DFS-обходе — то, что в итоге читает пользователь). Это позволяет отделить "сколько модель печатает" от "сколько контента она производит".

| Условие | Raw chars (avg) | Useful text (avg) | Text / Raw |
|---------|----------------:|------------------:|-----------:|
| t1/zs   | 3,402           | 832               | 24%        |
| t1/fs   | 1,680           | 724               | 43%        |
| t2/zs   | 4,969           | **2,304**         | 46%        |
| t2/fs   | 3,171           | 1,600             | **50%**    |
| t3/zs   | 3,366           | **593**           | **18%**    |
| t3/fs   | 4,373           | 760               | 17%        |
| t4/zs   | 6,063           | 2,128             | 35%        |
| t4/fs   | 6,128           | 1,477             | 24%        |

Три наблюдения:

**1. T2 — самая content-dense архитектура.** Содержательная плотность выхода (text/raw ratio) у T2 достигает 50%, выше чем у любой другой архитектуры. T2/zs выдаёт 2,304 useful chars — больше чем t4 (2,128) при вдвое меньшем raw output. Промежуточный текстовый шаг функционирует как **verbosity-preserving buffer**: модель сначала пишет содержательный текстовый ответ в обычном для себя объёме, и только потом структурирует его, не теряя контент на этапе разметки.

**2. T3 — content-starved при сравнимом raw size.** При raw output 3,366-4,373 chars (сопоставимо с t1) T3 выдаёт всего 593-760 useful chars — **82% выходных байт уходит на структурные wrappers AXtree-формата** (parentId/childIds, role-value pairs, properties arrays). Это объясняет систематически низкие manual rating у T3 (1.8/2.4): человеческий рейтер получает короткий по содержанию widget при том же объёме API-вызова. T4 находится в промежуточном положении: 24-35% text/raw — выше T3 за счёт сохранения content через text-этап, но ниже T2 потому что AXtree-разметка съедает значительную долю байт.

**3. Few-shot уменьшает useful content в 3 из 4 архитектур — количественное подтверждение verbosity matching:**

| Архитектура | useful chars zs → fs | Δ |
|-------------|---------------------:|--:|
| T1          | 832 → 724            | **−13%** |
| T2          | 2,304 → 1,600        | **−31%** |
| T3          | 593 → 760            | **+28%** |
| T4          | 2,128 → 1,477        | **−31%** |

T1, T2, T4 теряют content при добавлении few-shot — модель anchors на verbosity примеров, которые в эксперименте короткие. T2 и T4 теряют по 31% — наибольший эффект, потому что их zs-бэйслайн особенно verbose.

T3 — **единственная архитектура где few-shot увеличивает content** (+28%). Объяснение: T3/zs работает в чужом для модели формате (AXtree) и осторожно выдаёт минимум; few-shot примеры показывают "вот так можно подробнее", и модель раскрепощается. Это edge case: обычно few-shot гасит verbosity, но не если zs-бэйслайн уже неприлично краток.

Этот анализ количественно подтверждает качественное наблюдение из manual rating (см. 2.6, пункт 3): T1/fs получает rating 3.4 (ниже t1/zs 4.8) именно потому что выдаёт 724 useful chars против 832 у zs — человек видит более скудный widget. T2/fs не страдает от этого эффекта в том же масштабе (1,600 useful chars остаются конкурентоспособными по объёму), что объясняет почему T2 удерживает rating 4.8 в обоих shot-режимах.

### 2.8. Соотношение структурной и семантической дисперсий

Во всех архитектурах структурная дисперсия превышает семантическую в 2-7×:

- t1: struct=0.370 / seman=0.080 / ratio=4.6×
- t2: struct=0.234 / seman=0.020 / ratio=12.0×
- t3: struct=0.361 / seman=0.103 / ratio=3.5×
- t4: struct=0.380 / seman=0.102 / ratio=3.7×

Это значит, что **модель устойчива в выборе контента, но нестабильна в его структурном представлении**. От прогона к прогону содержательно сохраняется тот же набор фактов и идей, но способ их разложения по дереву (как hbox vs vbox, через listitems vs через headings, с inline-описаниями vs со ссылками) варьируется существенно.

T2 — выраженный outlier: ratio=12× (структура варьируется, семантика почти константна), что вытекает из его архитектуры: основной content уже зафиксирован промежуточным текстом первого вызова, и второй вызов лишь по-разному структурирует один и тот же материал.

## 3. Выводы

### 3.1. Основные выводы

1. **Widget-формат продуцируется frontier-LLM напрямую через prompting.** T1/fs и T2/fs достигают 97.8% и 100% строгой валидности соответственно. Это меняет позиционирование формата: он не только мишень для специализированного fine-tuning'а, но и универсальная цель, доступная через стандартные prompting-техники.

2. **Простая архитектура побеждает.** Прямая генерация (T1) и текст-опосредованная генерация (T2) превосходят AXtree-опосредованные пайплайны (T3, T4) по строгой валидности. Гипотеза о пользе известного веб-стандартного промежуточного формата (AXtree) не подтвердилась — длиннее пайплайн, больше точек отказа.

3. **Few-shot — критический фактор стабильности.** Снижение структурной дисперсии 28-39% во всех архитектурах, семантической — до 64% при высокой температуре. Эффект усиливается с ростом температуры (anchor важнее когда у sampling больше свободы).

4. **Структурная и семантическая стабильность диссоциируют.** Семантическая дисперсия в 2-7 раз ниже структурной во всех условиях — модель решает что сказать стабильно, но как разложить это по дереву варьирует. Для целей, требующих воспроизводимости структуры (например, как обучающие данные для tree-based задач), это требует именно few-shot anchor'a.

5. **Адаптеры пайплайна маскируют ошибки модели.** Пермиссивный `chrome_axtree_to_widget` восстанавливает значительную часть структурно-сломанных AXtree-выходов в валидные widgets. Для честной оценки способностей модели валидность измеряется до адаптера; recovery остаётся feature системы, но не достижением LLM. Manual rating subset'a эмпирически подтверждает этот выбор: ручная оценка лучше согласуется со strict (pre-adapter) метрикой, чем с widget-level.

6. **Few-shot anchor имеет нетривиальный побочный эффект — verbosity matching.** Снижая дисперсию структуры, few-shot также фиксирует модель на длину и детализацию примеров. Эффект подтверждается количественно: useful text content падает у T1 на 13%, у T2 и T4 на 31% при переходе от zs к fs. T1/fs становится валидным но содержательно-скудным (724 useful chars против 832 у T1/zs; manual mean 3.4 при автоматической валидности 98%). T2 теряет меньше относительно своего объёма и удерживает manual rating 4.8 — промежуточный текстовый шаг работает как verbosity-preserving buffer. Это означает, что для production-use few-shot примеры должны подбираться не только по структурной корректности, но и по целевой длине ответа.

7. **AXtree-формат расточителен по байтам.** T3 расходует 82% выходных байт на структурные wrappers (parentId/childIds, role-value pairs). T4 — 65-76% оверхеда. T2 — 50% (текст в `name`-полях). T1 — 24-43%. Это не только косметика: больший процент токенов на bookkeeping означает меньше attention budget'a на содержательное планирование ответа, что согласуется с архитектурным выводом о слабости длинных AXtree-пайплайнов.

### 3.2. Практические рекомендации

- Для приложений, требующих максимальной валидности и стабильности: **T2 (text-mediated widget) с few-shot** — 100% валидность, минимальная дисперсия, content-stable. Manual rating подтверждает: mean 4.8/5 при N=5.
- Для приложений, чувствительных к стоимости (один LLM-вызов вместо двух): **T1 (direct widget)** — но выбор между zero-shot и few-shot зависит от приоритета. T1/fs даёт высокую валидность но скудный контент (manual 3.4); T1/zs наоборот — ниже валидность но более content-rich (manual 4.8). Если используется T1/fs, few-shot примеры должны подбираться по целевой длине ответа.
- AXtree-промежуток (T3, T4) **не рекомендуется** для widget-генерации.

### 3.3. Импликации для основного проекта (fine-tuning)

Изначальный план — fine-tune модель для генерации в widget-формате — остаётся валидной задачей, но контекст изменился: базовая способность frontier-LLM к этому формату подтверждена. Fine-tuning теперь должен мотивироваться не "научить модель формату", а более конкретными задачами:

- **Снижение требований к промпту** (one-shot или zero-shot вместо few-shot)
- **Меньшие модели** (locally-runnable open-weight models, где widget-валидность zero-shot заметно ниже)
- **Доменная специализация** (под конкретный класс UI-задач)

### 3.4. Ограничения

- **Eval-set N=25**: синтетические вопросы, ограниченная репрезентативность реального распределения пользовательских интентов.
- **Одна модель**: только gpt-4o. Поведение open-weight моделей и более слабых проприетарных может отличаться существенно — особенно по строгой валидности в zero-shot.
- **Дискретный набор температур**: T ∈ {0, 0.4, 0.8} — для точного описания температурной кривой нужно больше точек.
- **Permissive adapter как часть системы**: для T3/T4 пайплайн содержит детерминированный шаг, который, если изменить (на более строгий), результаты сместятся. Это часть архитектурного выбора, не источник смещения, но требует фиксации.
- **TED-сравнение по labels=type+hints**: не учитывает содержимое `name`-полей в структурной метрике — это намеренное разделение метрик (структурная и семантическая считаются отдельно), но в некоторых задачах может маскировать "структурно одинаковое, семантически разное".
- **Manual validation на subset'е**: субъективный rating проведён на 40 карточках (5 на условие) одним рейтером по 5-балльной Likert-шкале. Этого достаточно для качественной валидации автоматических метрик и обнаружения trade-off'ов вроде verbosity matching, но не для формального статистического сравнения архитектур (N=5 на условие даёт высокий sampling noise — для этого нужно ≥30 карточек на условие и множественные рейтеры с inter-rater agreement).

### 3.5. Направления для будущей работы

- Расширение eval-set до 100+ вопросов с реальным распределением из WebUI-датасета.
- Воспроизведение эксперимента на open-weight моделях (Llama-3, Qwen, etc.) для проверки переносимости findings.
- Fine-tuning эксперимент на основе результатов: какой объём supervised данных нужен, чтобы догнать T2/fs gpt-4o валидность на меньшей модели.
- Multimodal-расширение: вопрос + изображение → widget (соответствует основной мотивации проекта).
